# Creating and organizing channels

Choose the destination server first, then open channel creation. The form offers text, voice, video, forum, announcement, rules, media and read-only channels when the Tavern policy module is enabled. Each choice describes its actual behavior and exposes a purpose, icon and message slow-mode setting. Voice/video choices keep a persistent encrypted chat; creating them never opens a camera or microphone. Calls still require the instance call configuration.

The chosen kind and slow-mode values are written as initial `io.tavern.channel` state. Rooms are invite-only, nonfederated and Megolm encrypted, with `joined` history visibility. Announcement, rules and read-only rooms additionally start with native message/encrypted posting power 50; current custom moderation permissions remain required. Changing a channel's type later does not itself grant native posting power. Forum rooms reuse the existing titled/tagged discussion and thread interface. Media rooms accept encrypted attachments and ordinary messages; encrypted message contents are not classified by the homeserver as “file-only.”

Server and category placement are checked against fresh native membership, native state permissions and applicable custom channel-management grants. Canonical reciprocal parent Spaces are bounded to 32 scopes and depth 8; their permissions must remain available. Category permission boundaries retain the existing owner-only rule. A server invitation does not automatically grant membership or message keys in each channel. The form offers explicit member invitations separately from room creation and placement.

Creation and subsequent server linking, category placement and invitations are separate native operations. If a later step fails, the form retains the created room ID, confirms completed steps and offers **Retry remaining setup** for that same room. A previously accepted invitation is read back before retry so it is not blindly replayed. **Open channel** permits manual management; a partially linked channel also remains accessible from **All conversations**. Pending setup is kept in the current form, not as a durable background job. An ambiguous creation response cannot reliably reveal a missing room ID: check All conversations before creating again.

Drafts, completion callbacks and retries are tied to the current client, user, device and browser account generation. Replacing the server or account retires the visible draft and suppresses late callbacks. Native authorization remains authoritative; separate state reads do not provide a cross-room atomic transaction.

Validation: `tests/channel-creation.test.mjs` checks actual model initial state, authority/category boundaries, inherited policy, copied-state changes, partial setup, ambiguous invitation acknowledgement, privacy/topology changes and owner retirement. `tests/browser/channel-creation.spec.ts` mounts the real form/model with controlled native transport and covers voice configuration, category/member outcomes, same-room repair, server/account replacement, behavior guidance and a 320px viewport. Live native creation continues to use the production Matrix SDK; these browser tests do not claim a deployed media connection.
