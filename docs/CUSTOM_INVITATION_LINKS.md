# Custom invitation links

Server managers can choose an optional readable name when creating an invitation, for example `https://tavern.example/invite/guild-night`. The name belongs permanently to that specific invitation. It cannot be renamed, moved to another invitation, renewed by replacement, or reused after expiry, revocation, account deactivation or deletion of the original invitation record. Create a new name when you need a replacement invitation.

Names use 3–48 lowercase ASCII letters, numbers or single hyphens, with a letter or number at each end. A small set of application names is reserved. Names are unique across the instance. The database reserves the name and creates its invitation in one transaction; conflicting requests receive a conflict without creating an orphan invitation. A separate permanent reservation record prevents reuse even if the original invitation is removed.

Publishing a name requires current membership in a local, non-federated Matrix Space, current native state and invite power, and the server's `manage_server` and `invite` permissions. Before server roles exist, only the native server creator can publish one. The account API checks authority again after loading shareable invitation metadata. Naming a link does not create or change a Matrix room alias.

Custom names are public and guessable. Anyone who finds a working link can preview the shared server name. Email and domain restrictions still control acceptance; they do not make the readable name a secret. The management screen explains this before creation. Custom links can be copied again from the invitation list. Existing random invitation secrets remain available only in the creation response and are stored as hashes.

A readable link uses the existing invitation record and acceptance process. Its expiry (1–720 hours), use limit (1–1,000), verified-email restrictions, default roles, reservation accounting and resumable acceptance all remain in force. Readable and random handles for one invitation share the same usage counter. Sign-in, account security setup and verified-email registration use the same existing gates; supplying a readable path does not override instance registration policy. Closing an invitation preserves unrelated query parameters and the current room hash.

Revocation, expiry and the recipient's current verified email are checked again after remote waits and before the next native invite or join. Native issuer authority includes the inherent creator power in room version 12. A request already in flight at Synapse cannot be atomically cancelled by changing a local invitation record. Revoking a link does not withdraw a native invitation already sent, remove a joined member or undo previously assigned roles. Uncertain reservations remain consumed so a retry cannot exceed the use limit; native membership remains authoritative.

Focused validation covers actual account-API HTTP requests against the test Matrix service, concurrent creation and last-use races, native/custom permission changes, permanent reservations after cleanup, email registration, and revocation during token issuance or native invite delivery. Frontend model/browser checks cover path parsing, existing query links, account/room changes during asynchronous work, creation and acceptance. These tests do not claim a new live Synapse deployment acceptance result.
