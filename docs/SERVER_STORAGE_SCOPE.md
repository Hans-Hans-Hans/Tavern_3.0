# Server storage quota scope

The requested per-server attachment quota in brief §39 remains incomplete. Current Tavern enforces account and instance upload byte limits. It cannot securely determine the total media referenced by encrypted messages in a Matrix Space while preserving the current encryption and supported-client protocol.

`UploadQuota` in [api/admin_resources.py](../api/admin_resources.py) buffers bounded upload bodies, measures actual bytes and atomically reserves account/instance capacity before forwarding to Synapse. Defaults are 10 MiB per upload, 1 GiB per account and 10 GiB per instance. Transport-uncertain reservations remain charged until reconciliation. Initial reconciliation imports local media usage by uploader; it does not recover a destination room or Space. Native generated thumbnails, remote media caches, message databases and backups are outside this accounting. Tavern's separately uploaded encrypted previews are ordinary local uploads and therefore count.

The managed [API proxy](../api/server.py) routes supported uploads through that quota service and rejects other media writes. The public [Nginx gateway](../docker/npm/server.conf.template) blocks native upload/create aliases in managed mode, including Synapse's legacy `media/v1/upload`. This boundary does not apply to an independently exposed internal Synapse port or to legacy unmanaged mode. [Built gateway checks](../scripts/ci-gateway.py) exercise raw and encoded aliases against Nginx in CI.

The missing attachment attribution is inherent in the current protocol:

- [lib/matrix.ts](../lib/matrix.ts) encrypts attachments locally, uploads ciphertext without a room parameter, then includes the MXC URL, file information and decryption material inside the encrypted message. Profile/artwork uploads use the same media repository through [lib/community.ts](../lib/community.ts) or [lib/api.ts](../lib/api.ts).
- Synapse 1.160.0's native upload handler passes content type, name, bytes, length and the authenticated uploader to media storage. It receives no destination room. Its upload route includes `r0`, `v1` and `v3`. [Pinned upload resource](https://github.com/element-hq/synapse/blob/v1.160.0/synapse/rest/media/upload_resource.py).
- The public media spam callback receives a readable file and `FileInfo`. That metadata identifies the media ID, origin and thumbnail/cache context; it does not provide an attachment's destination. Local media records retain uploader and byte length, not an authoritative Space association. [Pinned callback](https://github.com/element-hq/synapse/blob/v1.160.0/synapse/module_api/callbacks/spamchecker_callbacks.py), [FileInfo](https://github.com/element-hq/synapse/blob/v1.160.0/synapse/media/_base.py), [media repository](https://github.com/element-hq/synapse/blob/v1.160.0/synapse/media/media_repository.py).
- The native [Tavern policy](../synapse_modules/tavern_policy.py) can enforce current sender, membership, canonical-parent and permission rules for `m.room.encrypted`. It cannot inspect that event's plaintext attachment descriptors.

A client-provided room header or signed upload receipt cannot close this gap. A client can upload under a personal or different server scope, reuse existing media, or reference remote media, then put that descriptor inside ordinary encrypted content. A receipt can prove which uploaded bytes were charged to its budget; it cannot prove that opaque ciphertext contains only those bytes' references. Requiring receipts only for declared attachments is bypassable. Requiring a declaration on every encrypted message still does not make an empty or incomplete declaration truthful. Client-side checks would not constitute native server enforcement.

An explicitly named **server-funded upload budget** could track immutable storage ownership for uploads charged to it, with real membership checks and atomic reservations. That is a narrower accounting feature: reuse elsewhere, unscoped uploads and old encrypted history would not establish total attachment usage in a Space. It has not been implemented or substituted for the requested quota. No historical Space attribution, MIME classification, plaintext inspection or stronger native enforcement is claimed. Closing the full requirement needs a separately justified protocol change; this limitation does not justify weakening end-to-end encryption.
