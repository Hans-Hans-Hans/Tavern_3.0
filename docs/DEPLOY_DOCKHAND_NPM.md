# Deploy Tavern with Dockhand, NPM, and Cloudflare

For builds directly from GitHub `V3`, start with [the GitHub deployment guide](DEPLOY_GITHUB.md). This guide retains the local-image recipe and shared NPM/DNS configuration.

This recipe uses **one hostname**, such as `chat.example.com`. It serves the Tavern client and Matrix API behind your existing Nginx Proxy Manager. Accounts become `@name:chat.example.com`; choose that domain before creating accounts and keep it stable.

Tavern does not publish host ports. NPM reaches `tavern-web:8080` over a shared Docker network. The database and Synapse stay on a separate internal network. Keep Dockhand and the NPM administration UI restricted to your trusted network.

## 1. Put the source on your Docker host

Extract the source archive into `/opt/stacks/tavern`, with `Dockerfile` and `compose.yaml` directly inside that directory. The examples below assume NPM and Tavern run on the same Docker host. You need Docker Engine with Compose and Python 3; Node.js is installed inside the build image.

Choose a supported, pinned image from the [official Synapse releases](https://github.com/element-hq/synapse/releases). Replace `vX.Y.Z` below with that exact release; the helper deliberately rejects `latest`.

```sh
cd /opt/stacks/tavern
sudo python3 docker/prepare-npm.py \
  --domain chat.example.com \
  --synapse-image matrixdotorg/synapse:vX.Y.Z \
  --data-dir /opt/tavern-data
sudo chown -R 991:991 /opt/tavern-data/synapse
docker build --target npm -t tavern:0.3.0 .
```

The helper creates new server secrets under `/opt/tavern-data` and a private `.env` in the source directory. The `.env` contains deployment addresses and paths; database passwords stay in files. Existing configuration/data is never overwritten. Back up the data directory, including the signing key generated by Synapse at first startup.

The image is built on your host. `tavern:0.3.0` is a local image tag, not a published Docker Hub image.

## 2. Connect NPM to the proxy network

```sh
docker network create npm_proxy
```

If the network already exists, reuse it. Add `npm_proxy` to the NPM **application service’s** networks while preserving its current networks and database connection. At the top level of the existing NPM Compose file, declare:

```yaml
networks:
  npm_proxy:
    external: true
    name: npm_proxy
```

For example, if NPM currently uses its default network, its application service would use:

```yaml
services:
  app:
    # Keep the existing image, ports, volumes, environment, and other settings.
    networks:
      - default
      - npm_proxy
```

Apply that change to your existing NPM stack. Do not replace the whole stack with these fragments. A shared Docker network avoids exposing upstream ports on the host. [NPM documentation](https://nginxproxymanager.com/advanced-config/#best-practice-use-a-docker-network)

## 3. Deploy in Dockhand

Select the Docker environment on which you built the image. Create a stack named `tavern`, paste **`compose.dockhand.yaml`**, and provide these variables in its environment editor:

| Variable | Example |
|---|---|
| `TAVERN_DOMAIN` | `chat.example.com` |
| `SYNAPSE_IMAGE` | The same pinned tag used in step 1 |
| `TAVERN_DATA_DIR` | `/opt/tavern-data` |
| `NPM_PROXY_NETWORK` | `npm_proxy` |

Deploy the stack. The image-only Compose file avoids requiring Dockhand to read a local build context. Absolute bind paths refer to the selected Docker host; deploying to another environment without those files will fail. `pull_policy: never` applies only to the locally built Tavern image. Synapse and Postgres are pulled normally.

For a Git-managed stack, `compose.yaml` also includes the build definition. Configure matching filesystem paths, a valid source context, and **Build images on deploy**. [Dockhand documentation](https://dockhand.pro/manual/)

## 4. Add the NPM proxy host

| NPM setting | Value |
|---|---|
| Domain Names | `chat.example.com` |
| Scheme | `http` |
| Forward Hostname / IP | `tavern-web` |
| Forward Port | `8080` |
| Cache Assets | Off |
| Websockets Support | On; required for conference signaling |
| SSL certificate | Valid certificate for `chat.example.com` |
| Force SSL | On |

Use these directives in the proxy host’s Advanced field:

```nginx
client_max_body_size 12m;
proxy_read_timeout 90s;
proxy_send_timeout 90s;
proxy_buffering off;
```

All Matrix paths go through this same proxy host. Tavern forwards only client/media routes and rejects federation/admin routes. Do not add public mappings directly to Synapse or Postgres. API authentication is Matrix authentication; adding an interactive NPM access login in front of the Matrix API will break clients.

## 5. Point Cloudflare DNS at NPM

Create an A record for `chat.example.com` pointing to your public IP. Only create an AAAA record if IPv6 reaches NPM correctly. Forward TCP 443 on your router to NPM’s existing HTTPS listener. Certificate issuance may also need port 80, or use NPM’s DNS challenge with a narrowly scoped DNS API token.

**Start with DNS-only (gray cloud).** Browsers then connect directly to your NPM certificate. If you choose Cloudflare proxying later, use **Full (strict)**, keep a valid origin certificate, and bypass caching for the entire Tavern hostname. Disable script rewriting, Rocket Loader, and browser challenges on this hostname/API. Never use Flexible TLS. [Cloudflare Full (strict)](https://developers.cloudflare.com/ssl/origin-configuration/ssl-modes/full-strict/)

With orange-cloud proxying, Cloudflare terminates HTTPS and is a trusted intermediary for login requests and delivered client code. Matrix E2EE encrypts message content separately; it does not make login credentials, all metadata, or delivered JavaScript invisible to the HTTPS intermediary. DNS-only is the default recommended here for the self-hosted privacy goal.

## 6. Create accounts

From the source directory on the Docker host:

```sh
sudo docker compose exec synapse register_new_matrix_user \
  -c /data/homeserver.yaml http://localhost:8008
```

Enter the username and password interactively. Registration is closed to the public. Create an administrator only when required, then repeat for a second regular test account.

Open `https://chat.example.com`, choose **Connect homeserver**, and sign in. The server address is prefilled and locked to this instance. Create a server, create a channel inside it, and invite another account. Server and channel membership are separate; invite the person to both when needed.

## 7. Check before use

```sh
python3 docker/verify-deployment.py https://chat.example.com
sudo docker compose ps
```

The verifier checks HTTPS, the client/config endpoint, Matrix version discovery, and rejected public admin/federation paths. It does not prove message encryption or perform a security audit. Use two browser profiles to check messages, invitations, encrypted attachments, threads, moderation, key export/import, and session revocation. Test a restore from backup before treating the deployment as reliable.

The package was compiled and checked locally. This development environment has no Docker daemon or access to your host, so container startup and NPM routing have not been exercised here.

## Backup and upgrades

Stop Synapse writes while taking a consistent PostgreSQL dump and a backup of `/opt/tavern-data`. Keep the database, media, server signing key, configuration, and database password together. Client key exports are separate and are needed for encrypted history recovery in this release. The [Caddy guide’s backup procedure](../docker/README.md#backup-and-restore) illustrates `pg_dump`; use the data path in this recipe.

Keep the same domain, stack name, volumes, and data paths on upgrades. Build a new Tavern image tag, update the Compose image tag, and deploy it after testing. Pin/test Synapse updates separately. Never use `docker compose down -v` to update or reinstall an existing instance.

## Tavern 0.3 call and integration services

Follow [calls and integrations](CALLS_AND_INTEGRATIONS.md) after this base setup. `compose.dockhand.full.yaml` adds the media and bot services with the same source-built image approach. The base stack still publishes no host ports; TURN/SFU services intentionally publish the direct media ports listed in that guide. General federation stays blocked, with an explicit OpenID userinfo exception for conference authorization.
