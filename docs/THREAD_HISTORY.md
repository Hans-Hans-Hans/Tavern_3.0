# Historical thread replies

Opening a public thread uses the room's existing Matrix SDK thread timeline. A historical root found through saved messages or a message link can come from Tavern's event cache; the root must still match both the requested event ID and joined room. A missing or cross-room cache entry requires a native event lookup in that room. State events and replies to another thread cannot become a new thread root.

Matrix SDK 42.3 starts initialization inside `Room.createThread`. Tavern coalesces concurrent initial reads and waits for the public `initialEventsFetched` flag and `ThreadEvent.Update` lifecycle. It does not call the SDK's private metadata methods, start a competing `getLatestTimeline` request, or filter relations to the unencrypted `m.room.message` wire type. Encrypted replies stay in the SDK timeline and pass through the ordinary event decryption and message projection. An initialized thread with no replies is a successful empty result.

Reply placement uses the SDK's wire relation rather than requiring decrypted content. A reply whose keys are missing therefore retains its existing decryption-error placeholder inside the correct thread instead of disappearing from the results.

The existing **Load 50 earlier replies** control follows the thread's own backward pagination token. Concurrent requests share one page fetch. Reaching the start stops further pagination, while a rejected page preserves the cursor for an ordinary retry. Thread message API reads require a conversation; their `hasMore` result reflects thread history rather than the containing room's history.

Every initial read, page completion and projection checks the captured Matrix client, joined room object and thread identity. Account changes, departure, model replacement or a reset of the live timeline cannot publish a late page into the current view or global event cache. SDK requests already in flight may finish inside the old SDK model, but Tavern rejects their result. Initialization observers and timers are removed on completion, deletion, access loss or the 20-second deadline.

The pinned SDK does not expose a public promise/error/retry method for its initial metadata load. If initialization never reports completion, Tavern reports that history could not finish and asks the user to reconnect their Matrix session and reopen the thread. It does not turn that failure into a claim that the thread has no replies or mutate private SDK flags to force recovery.

`tests/thread-history.test.mjs` exercises actual pinned SDK `Room`, `Thread`, native HTTP parsing and timeline pagination, including cached opaque root IDs, encrypted wire replies, empty threads, cursor reuse, server errors, access changes, stalled initialization and cleanup. It also runs the actual Matrix message API and normalizer to verify thread cursors, missing-key placeholders and protection of the next account's event cache. `tests/browser/thread-history.spec.ts` uses the unchanged `ThreadTools` component with that SDK fixture to verify loading, empty results, retry and account-change behavior. Fixture decryption supplies test plaintext through the public event decryption API; these tests cover history routing and ownership, not cryptographic security or an external homeserver. Existing live encrypted multi-user tests remain the deployment proof for real encryption.
