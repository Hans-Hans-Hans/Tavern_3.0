# Historical thread replies

Opening a public thread uses the room's existing Matrix SDK thread timeline. A historical root found through saved messages or a message link can come from Tavern's event cache; the root must still match both the requested event ID and joined room. A missing or cross-room cache entry requires a native event lookup in that room. State events and replies to another thread cannot become a new thread root.

Matrix SDK 42.3 starts initialization inside `Room.createThread`. Tavern coalesces concurrent initial reads and waits for the public `initialEventsFetched` flag and `ThreadEvent.Update` lifecycle. It does not call the SDK's private metadata methods, start a competing `getLatestTimeline` request, or filter relations to the unencrypted `m.room.message` wire type. Encrypted replies stay in the SDK timeline and pass through the ordinary event decryption and message projection. An initialized thread with no replies is a successful empty result.

Reply placement uses the SDK's wire relation rather than requiring decrypted content. A reply whose keys are missing therefore retains its existing decryption-error placeholder inside the correct thread instead of disappearing from the results.

The existing **Load 50 earlier replies** control follows the backward pagination token on the thread's oldest connected SDK timeline segment. A null token on the live segment alone does not mean history is complete. Reads include at most 256 segments linked reciprocally within that exact thread timeline set; disconnected cached segments stay outside the result until native linking establishes continuity. Concurrent requests share one page fetch. Reaching the start stops further pagination, while a rejected page preserves the cursor for an ordinary retry. Thread message API reads require a conversation; their `hasMore` result reflects thread history rather than the containing room's history.

Every initial read, page completion and projection checks the captured Matrix client, joined room object and thread identity. Account changes, departure, model replacement, timeline resets or relinking cannot publish a late page into the current view or global event cache. These checks also run after decryption finishes. A legitimate SDK merge during a request can require a fresh retry against the newly connected segments. SDK requests already in flight may finish inside the old SDK model, but Tavern rejects their result. Initialization observers and timers are removed on completion, deletion, access loss or the 20-second deadline.

The pinned SDK does not expose a public promise/error/retry method for its initial metadata load. If initialization never reports completion, Tavern reports that history could not finish and asks the user to reconnect their Matrix session and reopen the thread. It does not turn that failure into a claim that the thread has no replies or mutate private SDK flags to force recovery.

The thread panel's participant list uses native event senders from the original message and its direct thread replies. Expand **participants found**, then choose **Discover earlier participants** to include authors outside the loaded history. Names and full Matrix IDs are searchable within that list. Membership labels describe currently loaded room membership; public threads do not have separate membership. A person who left the room can still appear as a historical author. A pending local event, reaction, edit, redacted event or reply to another thread does not add a participant.

Discovery uses the same SDK pagination as **Load 50 earlier replies**, without requiring message decryption or writing a new participant index. Each explicit run reads at most 20 pages of 50 events, with a 20-second deadline per page, 20,000 loaded-event limit and 5,000-author limit. Empty pages can advance to older authors; stalled or repeating cursors produce an error. A partial run offers **Continue participant discovery**. Reaching the beginning means only the history available to this account: deleted, hidden and unavailable history can still omit people. Native history denial is an error, not an empty or complete list.

Stopping discovery prevents subsequent progress from that run. It does not abort a shared SDK page request another history reader may need, so an ordinary timeline update can still reveal that page's authors. Account, device, API-session generation, joined-room and thread-timeline checks reject late discovery results. Thread reply refreshes also retain only the latest response for the current view; closing and reopening the same thread cannot revive an older response. Replies are hidden immediately when their captured view no longer matches. The selected root is bound to its originating account and joined room; changing accounts or losing room access closes that thread panel.

Available decrypted historical replies follow the existing SDK timeline/decryption events into Tavern's encrypted local search index. Author discovery does not make undecryptable bodies searchable and does not search message bodies to identify participants.

`tests/thread-history.test.mjs` exercises actual pinned SDK `Room`, `Thread`, native HTTP parsing and timeline pagination, including cached opaque root IDs, encrypted wire replies, empty threads, cursor reuse, server errors, access changes, stalled initialization and cleanup. It also runs the actual Matrix message API and normalizer to verify thread cursors, missing-key placeholders and protection of the next account's event cache. `tests/thread-participants.test.mjs` adds historical sender discovery, exclusions, continuation, shared pagination, cancellation and owner checks; `tests/thread-reply-refresh.test.mjs` tests response ordering and cleanup. `tests/browser/thread-history.spec.ts` uses the actual `ThreadTools`, SDK timelines and local IndexedDB search. `tests/browser/thread-workspace.spec.ts` checks the mounted Workspace thread panel against delayed and reversed read responses. Fixture decryption supplies test plaintext through the public event decryption API; these tests cover routing, projection and ownership, not cryptographic security or an external homeserver. Existing live encrypted multi-user tests remain the deployment proof for real encryption.
